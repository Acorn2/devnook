# DevNook 开发缘起：从端口冲突到本地开发工作台

整理日期：2026-11-15。本文依据 hresh 提供的三张网页版 GPT 对话截图、本地 Codex 相关历史对话、原始需求文档和项目实施记录整理。用途是保存项目为什么开始、需求如何形成，以及开发中哪些反馈进一步明确了方向。

**DevNook 最初要解决的，是多项目开发时对本机运行状态失去掌握的问题：AI 已经启动了前后端服务，开发者却不清楚哪些还在运行、占了什么端口、属于哪个项目；等到自己再次启动，才通过端口冲突发现它们。** 随着讨论深入，需求逐渐连成一条完整流程：找到项目、用习惯的工具打开、启动需要的服务、查看实际端口与日志，并在需要时安全停止或重启。

这条流程来自 hresh 自己的开发困扰。现有材料能证明个人需求、试用判断和具体开发反馈，尚不能据此证明普遍市场需求、商业规模或付费意愿。

## 1. 起点：AI 帮忙启动了服务，自己却不知道它还在运行

第一张截图里的提问很具体：

> “因为我有时候开发很多个项目，codex会自动部署前端或者后端服务，但是我并不清楚，每次我手动执行命令时提示端口号已被占用，非常麻烦”

这里的“部署”结合上下文指本机开发服务的启动，不是生产环境发布。hresh 当时首先寻找的是已有的开源工具，希望查清电脑上究竟运行了哪些 Node、Java 等服务。[S1]

这段话包含三个彼此相连的问题。

首先，多项目交替开发使服务分散在不同的项目目录、终端和开发工具中。其次，Codex 可以代为启动服务，但启动这件事未必进入开发者持续可见、可管理的统一列表。最后，开发者通常在下一次启动失败时才发现旧实例仍然存在。端口冲突成了问题暴露的时刻，而此前的运行状态一直不够清楚。

因此，只回答“端口被哪个 PID 占用”还不够。开发者接下来仍需判断：这是哪个项目？是不是之前启动的服务？现在能不能停？停完以后如何重新启动？这些判断才是从系统信息回到开发任务所需要的部分。

依据这段经历，可以把最早的动机归纳为：**让本机已经发生的服务启动变得可见，让开发者能够继续管理它。** 这是对原始材料的归纳，并非 hresh 当时使用过的产品口号。

## 2. 第二次澄清：查到端口以后，还要能回到项目继续开发

第二张截图把需求从排查占用进一步推向日常使用：

> “我并不只是想查看tpc监听情况，我有更直接的需求，比如说这个端口号对应什么项目服务呀，是否支持快速打开项目呢？是否支持我关闭重启呢？”

同一段话还描述了原先启动 Node 项目的过程：先用开发工具打开项目，再到终端窗口执行命令，hresh 认为这很麻烦。[S2]

### 2.1 项目归属比进程名称更接近实际问题

`node`、`java`、`python` 可以帮助识别运行时，却无法直接告诉开发者自己正在处理哪件事。尤其在多个项目同时运行时，同一种进程名会重复出现。

hresh 想知道的是“这个端口对应什么项目服务”。这使项目目录、项目名称、内部组件和运行实例之间的关系成为产品的基础。端口需要能回到项目，项目也需要能展示当前相关服务，而不能让用户每次重新对照路径和命令。

### 2.2 快捷打开与启动服务属于同一次工作

找到项目以后，下一步通常是打开编辑器、查看代码或启动前后端。如果项目库只负责收藏路径，服务工具只负责显示端口，开发者仍需自己在两边来回切换。

第二次提问把这些动作放在了一起：快速打开项目、关闭服务、重新启动。这说明 hresh 希望减少的是恢复一个项目开发现场所需的重复操作，而不仅仅是少输入一次查询端口的命令。[S2]

### 2.3 Java 与 Node 的使用习惯不能被当作同一种启动方式

hresh 特别提到，自己使用的 Java 服务可能依赖 IDEA，平时会手动启动 application；Node 和 Python 服务则相对容易通过命令启动。[S2] 本地后续对话也明确提到，hresh 自己做 Java 和 Node 开发。[L2]

这里应保留两层事实：这是 hresh 当时的使用方式和担忧；它并不意味着所有 Java 服务都只能从 IDEA 启动。原始需求后来将命令行服务管理和 IDEA Run Configuration 集成分成不同阶段，避免为了统一入口就假定所有项目都能直接还原成同一种启动配置。[D1]

到这一步，需求已经能够表述为：围绕已有项目，把打开开发工具、启动服务、查看端口和后续启停放进同一个工作入口。

## 3. 先找工具、再试用，最后才决定自己做

hresh 并非一开始就要求开发新产品。第二张截图里的请求是：先寻找能解决问题的工具；如果没有，再评估自己做是否可行、是否有价值。[S2]

第三张截图进一步记录了实际试用：

> “我分别下载了CodeDeck、localhost和Runbox，都试着使用了下，我觉得这三个项目各有优势，需要合并这三个项目才是我真正想要的。”

紧接着，hresh 分别表达了对运行中端口扫描、工程目录扫描、中文界面和菜单栏设计的偏好。[S3]

这段经历支持的结论是：**在 hresh 当时的试用中，想要的体验分散在几款工具里，因此产生了把这些能力组织到同一条使用流程中的想法。** 它不等于已经做过完整竞品评测，也不能证明当时或现在都不存在满足相同需求的工具。

截图中的 GPT 回复曾判断，没有发现同时完善覆盖 Java、Node、Python、IDEA、Codex 场景的成熟工具。本文只将它作为当时讨论中的助手判断，不将其当作经过本次独立核实的市场结论。[S2]

### 3.1 三类参考分别解决什么问题

第三张截图里提到的原始软件截图仅以缩略图出现，无法仅凭当前图片独立确认“图1、图2、图3”与软件名称的对应关系。结合随后形成的 PRD 和本地参考研究，项目采用的借鉴分工如下；这是文档记录中的分工，不是本次重新测试三款软件得出的排名。[D1]、[D2]

| 参考项目                  | 进入 DevNook 设计的重点                                           | 对最初困扰的作用                               |
| ------------------------- | ----------------------------------------------------------------- | ---------------------------------------------- |
| CodeDeck                  | 选择目录、发现候选项目、预览后导入、保存项目档案                  | 从磁盘上的工程进入可查找、可打开的项目库       |
| localhost                 | 端口与外部进程发现、项目与服务分层、共享后台 Core、CLI / MCP 入口 | 看见已经运行的服务，并让不同入口读取同一份状态 |
| Runbox / project-launcher | 中文项目工作台、项目与任务分离、日志、就绪检测、依赖与组合启动    | 将服务从“临时命令”变成可以持续管理的运行对象   |

hresh 说的“合并”，在后续设计中被落实为对产品能力和使用流程的整合。原始 PRD 明确要求不直接合并三个仓库；本地研究记录也说明，当前实现没有引入它们的源码或视觉资产。[D1]、[D2]

## 4. 从最初困扰形成的产品取舍

下面这些取舍，既见于原始设计，也在后续开发中持续得到修正。它们解释了 DevNook 为什么形成现在这样的结构，而不是单纯罗列已有功能。

### 4.1 用项目组织服务，保留一个项目有多个服务的现实

前端、后端和其他任务可能在同一仓库，也可能分布在不同项目。项目负责回答“我在做什么”，服务配置负责回答“怎么启动”，运行实例负责记录“这一次实际发生了什么”。[D1]、[D3]

这样的区分使项目可以先被发现和整理，服务可以按需配置，某次运行退出也不会让启动方式和历史记录一并消失。它还避免把一个前后端仓库拆成多份难以辨认的项目档案。

### 4.2 看见外部服务，与把它交给 DevNook 管理，是两个动作

最初的问题恰好涉及 DevNook 之外已经启动的服务。如果只展示自己启动的进程，产品就会遗漏最需要解释的那些端口。

但发现进程、判断项目归属，并不自动赋予它托管身份。后续实现保留外部服务标记；需要改由 DevNook 管理时，先准备独立配置，再由用户明确确认，正常停止旧实例并启动新实例。[D3]、[D4]

这一区别直接关系到用户能否理解当前状态：保存配置后，原服务可能仍在运行；普通启动遇到占用应被阻断；切换托管则意味着一次可能短暂中断的重启。它们不能用同一个“已经接管”的说法带过。

### 4.3 运行状态必须能被实际证据解释

起因是“不知道本机到底启动了什么”，因此界面不能再用配置值代替真实情况。预期端口不等于实际端口，进程存在不等于网页可访问，没有 TCP 监听也不等于项目一定停止。[D1]、[D3]

这也是为什么 DevNook 要区分配置、运行状态、实际监听和就绪检查，并在系统读取失败时显示未知。对这类工具而言，错误的确定状态会让开发者再次做出错误操作。

### 4.4 统一入口应该减少操作，而不能要求先学会整套配置模型

原始需求包含较多工程能力，但 hresh 的出发点是希望启动更方便。后续实施因此逐步采用清单识别、启动建议、单行命令和默认收起的高级设置：有明确依据的内容先填好，不明确时再让用户补充。[D3]

扫描、导入和保存配置仍然不执行项目命令。便利来自减少重复填写、复用已保存信息，而不是在用户没有明确启动意图时自动运行项目。

### 4.5 人和 AI 应继续使用同一份服务配置

AI 是最初问题的一部分，也是后续需要保留的协作方式。如果改由 DevNook 托管之后，只能回桌面手动操作，原先“让 AI 改代码并调试服务”的工作流就被切断了。

共享 Core、CLI 和 MCP 为桌面与 AI 提供同一套项目、配置、日志和运行记录。MCP 是可选接入方式，默认只读；它的意义来自复用这些对象，而不是仅仅因为参考项目也支持这一协议。[D1]、[D5]

## 5. 本地开发对话怎样进一步明确了初衷

2026-11-12 进入实施后，反馈很快从“把能力做出来”转向“它是否真正解决原来的问题”。以下按问题整理，避免把后来的功能倒写成最初就已经明确的全部计划。

### 5.1 启动后看不到端口，仍然没有解决最初的问题

2026-11-13，hresh 在本地对话中指出：启动某个项目服务后看不到端口；同时追问，能否把 Codex、WorkBuddy 已经启动的服务与扫描导入的项目对应起来。[L2]

这条反馈很关键。服务启停即使已经实现，如果项目页看不到实际监听，也不能知道 AI 之前启动的服务属于谁，最初的疑问仍然存在。

后续改动补齐了服务列表与详情的实际端口、项目内的外部服务汇总、导入后的关联刷新和必要时的手动归属确认。[D3] 它把“项目管理”和“端口管理”连接起来，而不只是让两个页面分别存在。

### 5.2 开发工具自己的监听，不应冒充项目服务

同一天，hresh 发现项目下出现 Codex 本体的监听，追问这类进程是否有必要出现在应用里、是否有实际价值。[L2]

这促使产品进一步区分开发工具自身与它启动的业务服务。Codex 或 IDE 在项目目录运行，并不意味着该项目的前后端已经启动。当前项目服务页聚焦有服务用途证据的进程，完整端口管理仍保留其他监听，供排查时查询。[D3]

这次收敛说明，最初想要的“看清运行状态”不等于把所有能发现的信息都堆到项目首页。

### 5.3 扫描应该帮助找到服务相关项目，而不是遍历一切

2026-11-13，hresh 对扫描量提出质疑：Python、Node、Java Spring Boot 项目都有特征，没必要逐个扫描大量普通文件；随后又指出，纯 iOS 工程不一定值得出现在这个工具中。[L2]

这两次反馈共同收紧了扫描的目的。一方面，根据项目清单与模块声明查找，避免源码和素材目录消耗大部分预算；另一方面，按运行用途区分本机服务与纯客户端工程，同时保留混合仓库中的后端、Swift 服务端、Expo / React Native 开发服务器等实际服务入口。[D3]

扫描能力因此服务于“发现接下来值得管理的项目和服务”，不再单纯追求识别种类和候选数量。

### 5.4 满屏 node，仍然回答不了“这是哪个项目”

2026-11-14，hresh 对服务记录提出明确要求：优先展示项目名称；一个项目有多个服务时再区分，而不是先展示技术类型。[L3]

这与第二张网页截图里的“端口号对应什么项目服务”是同一个问题。后续全局列表以项目名为主，进入单项目后以服务名为主，再用相对目录和实际端口区分；运行时、PID 等信息保留在辅助位置。[D3]

这里的变化是信息顺序：开发者先认出自己的项目，再查看技术细节。

### 5.5 服务启动以后，要能直接进入网页

在补齐服务详情时，hresh 明确要求快速打开前端服务对应的网址。随后又连续指出两类误判：有些 Node 服务是后端，不必突出浏览器入口；另一些自定义 Node 服务确实提供网页，不能一刀切隐藏。[L3]、[L4]

这些反馈使“启动成功”之后的下一步更明确。提供网页的服务应方便打开；API 的监听地址仍可查看；用途证据不足时，不能只根据运行时名称猜测。当前实现结合已核验监听与有限的 HTTP 根响应头证据处理入口展示，具体边界见架构与实施记录。[D3]、[D6]

这延续了最早减少重复操作的诉求：既然已经找到了服务，就应能方便进入它提供的页面。

### 5.6 托管以后，AI 还能不能继续操作

2026-11-14，hresh 在讨论外部服务切换时问：原服务由 Codex 启动，托管后是不是只能自己手动启停，应该怎样设计？[L6]

这个问题将早期对 MCP 用途的疑惑，转成了具体需求。第三张截图里，hresh 还表示不太理解 MCP；本地另一段对话也再次询问这一功能的作用。[S3]、[L5] 到这里，CLI / MCP 的实际用途变得清楚：让 AI 继续复用已保存配置，查询状态和日志，并在相应授权与确认下操作同一服务，而不再另起一套实例。

后续增加了已有配置的继续切换入口、准确的“未启动 / 已停止”状态，以及可复制的 AI 交接说明。2026-11-15，又将切换确认中的手输 PID 改为只读展示和明确的操作按钮，保留 Core 身份核验与独立确认。[D3]、[L6]

因此，AI 接入是从实际协作问题中逐渐明确的能力；它并不是最初为了使用某个协议而设定的目标。

| 不知道哪些服务正在运行   | 真实监听快照、进程详情、项目归属、外部服务展示         | 不是全系统任务管理器；读不到的信息显示未知，启动来源不能可靠判断时统一标为外部 |

| 每次重复启动操作         | 启动建议、保存配置、确认启停、日志与运行历史           | 建议不保证依赖已经安装；扫描与保存不执行命令                                   |
| 已有服务需要停止或重启   | 外部正常停止；独立配置后明确确认切换为托管             | 切换是旧实例退出后启动新实例，旧环境、日志和 IDE 调试会话不会迁移              |
| Java 开发依赖 IDEA 习惯  | 支持开发应用快捷打开和命令行服务配置                   | IDEA Run Configuration 插件仍属后续方向，不能写成已经接入                      |
| AI 启动后还要继续协作    | 共享 Core、CLI、可选 MCP、AI 交接指引                  | 不自动配置 AI 客户端，不默认授予控制权限，也不能保证通知未接入的旧会话         |
| 希望整套开发环境便于准备 | 启动方案、依赖就绪等待、失败回滚                       | 回滚只处理本次创建的运行，保留既有实例，不自动强杀                             |

## 8. 如何理解这次开发的价值

对 hresh 而言，价值首先来自把自己的开发环境重新变得可理解、可操作。它针对的是已经发生的具体困扰：多个项目并行、不同启动入口、重复查端口和命令，以及人和 AI 之间没有统一服务记录。

从这些材料可以提出一个有待更多用户验证的判断：如果其他开发者也经常在多个本地项目与 AI 编程会话之间切换，那么将项目、实际监听、可复用配置和日志放在同一个入口，可能减少他们重新查找和核对的工作。现有材料没有提供节省时间的实测、外部使用者留存或付费数据，因此不将这种可能性写成已经成立的产品收益。

后续判断功能是否值得做，可以继续沿用开发中已经反复出现的问题：开发者能否认出这个服务属于谁，能否知道它实际是否运行，能否完成下一步操作，以及操作后能否清楚知道发生了什么。已有反馈对扫描、命名、网页入口和托管确认的修正，都围绕这些问题展开。

## 9. 可供后续介绍使用的简短版本

以下是对已核对材料的转述，不是历史原话：

> DevNook 起于 hresh 在多项目开发中反复遇到的端口冲突。Codex 会帮忙启动前后端服务，但哪些还在运行、属于哪个项目，往往等自己再次启动失败后才去查。继续梳理后，需求扩展为一个完整入口：找到项目、用习惯的编辑器打开、复用启动配置、查看真实端口和日志，并安全停止或重启。hresh 先试用了 CodeDeck、localhost 和 Runbox，发现自己喜欢的体验分散在不同工具里，随后开始开发 DevNook。后续迭代又补齐了外部服务归属、明确的托管切换，以及人和 AI 共用服务配置的衔接。
