# 端口又被占用了，于是我做了 DevNook

我做 DevNook 的起因，是开发时反复遇到的一句提示。

端口已被占用。

我同时开发多个项目，也会让 Codex 帮忙启动前端和后端。有时候服务已经跑起来了，但我并不清楚本机还运行着哪些。等到自己再去执行启动命令，看到端口冲突，才知道已经有一个进程占在那里。

于是，原本只是想继续写点代码，又得先查一下，这是什么服务，属于哪个项目，还要不要留着。

这种麻烦反复出现以后，我就去网页版 GPT 里问，GitHub 上有没有开源工具，能帮我看清电脑到底启动了哪些服务。Node 也好，Java 也好，至少让我知道它们还在运行。

那时候，我还没有决定自己做一个产品。我先想找个现成工具，把这个问题解决掉。

聊着聊着，我开始补充自己的需求。因为只看见端口，其实还差一截。

知道某个端口被一个进程占了，我还是得找到它对应的项目。找到项目以后，我可能要打开编辑器，可能要停掉旧服务，也可能只是想重启一下。这些事情原来散落在不同的地方，要我自己把它们连起来。

就连正常启动一个 Node 项目，也常常得先用开发工具打开目录，再切到终端，输入命令。我想要的方便很直接，选中项目以后，能少走几步，尽快进入开发。

而且，我自己的工作里有 Java，也有 Node。Java 项目我习惯在 IDEA 里启动 application，其他服务又有各自的命令。只把终端里那一步搬进一个按钮，并不能涵盖我平时的用法。项目还得能交给我习惯的开发工具打开。

把这些要求放到一起以后，我才比较清楚，自己要找的是一个围绕本地项目的工作入口。端口冲突把问题暴露出来了，但我希望解决的，还有冲突发生前后那些来回查找、切换和操作。

后来，我下载了 CodeDeck、localhost 和 Runbox，分别试着用了一下。

这几款工具各有让我喜欢的地方。查看当前运行端口的方式、扫描工程目录的过程，还有中文界面和菜单设计，都有我觉得顺手的部分。

我当时在对话里表达得很直接，感觉需要把这三个项目合在一起，才是我真正想要的。

这并不是说它们都不好用。恰恰是试过以后，我对自己想要什么有了更具体的认识。我喜欢的几个环节，分散在不同工具里，而我的需求会连续经过这些环节。

我希望从项目列表出发，知道这个项目现在有哪些服务在运行，然后接着打开、启动、查看或者重启。尤其是 Codex 之前已经帮我启动的那些服务，也得能在这里找到。

于是，我开始做 DevNook。

所谓把几个工具的优点放到一起，后来也没有变成直接合并它们的代码。它们帮我明确了想要的体验，DevNook 则围绕自己的使用流程逐步实现。

开发开始以后，我发现，前面聊清楚了方向，具体做出来还是会有偏差。

有一轮，我启动了项目里的服务，却发现页面上看不到实际端口。我又追问，既然端口管理里能列出那些监听，为什么进入项目以后，不能直接看到它们和项目的对应关系？Codex、WorkBuddy 已经启动的服务，也应该能找回来。

这件事把我重新拉回了最初的问题。即使已经有了启动和停止按钮，如果我还是看不清哪个服务用了哪个端口，最早那份困扰就没有解决。

后面还有一个很小、却很影响使用的地方。服务列表里，进程的技术名称比项目名称更显眼，好几条记录看上去都是 node。

可我想找的是自己的项目。都是 node，我还得继续看小字、认目录，才能分清谁是谁。

所以我又要求调整，全局先让我看到项目名，进入某个项目以后，再区分里面的服务。技术信息留着，需要排查时再看。

这几次修改让我对 DevNook 的要求更明确了。发现了多少进程，并不能直接说明它好不好用。我打开这个窗口，是要认出自己的项目，知道它现在是什么情况，然后继续做事。

也有一些东西，做出来以后我觉得没必要那么突出。

比如我在项目目录里开着 Codex，它自己也可能有监听端口。这个信息被放进项目服务页以后，就容易让人以为项目的服务已经运行了。我还专门问过，这种东西有必要显示在这里吗，有人在乎吗？

我最初明明是想看清 Codex 帮我启动的前后端，结果连 Codex 自己的监听也一起摆了进来。信息更多了，却更难判断。

后来，项目服务页收紧了范围，完整的端口信息仍然可以去排查，但日常页面先照顾我要管理的那些服务。

这些调整没有让功能清单变得特别长，却让我觉得它离最初想要的东西更近了。

再往后，出现了一个更直接的问题。

原来由 Codex 启动的服务，如果改交给 DevNook 管理，以后是不是就只能由我自己点按钮启停了？

我在开发对话里追问过这件事。因为我仍然会继续用 Codex 写代码，让它检查日志、排查问题。如果服务搬到统一的地方以后，反而要求我每次自己回来操作，那原来的开发过程就被打断了。

最开始看参考项目的时候，我其实不太懂 MCP 有什么用，还专门问过。到了这里，它才对应上一个我能理解的具体问题，怎样让 Codex 继续操作已经放进 DevNook 的服务。

至于通过命令还是其他接入方式，对我来说是后面的事。先要保证，我和 Codex 能找到同一份启动配置，看到同一个服务的状态。它需要重启的时候，能继续沿用这里已经保存的东西，不用再另外启动一份。

外部服务切换的过程，也让我意识到界面必须把事情说明白。保存了一份配置，旧服务可能还在跑；真正切换时，要让旧实例退出，再启动新的。页面如果只给一个含糊的状态，我还是会回到原来的疑问，到底哪个在运行，我刚才的操作又做了什么。

所以，后面的修改一直在处理这些具体困惑。配置和实际运行要分清，切换会做什么要讲明白，AI 后续怎么继续管理也要有入口。

回头看，DevNook 是在这些使用反馈里一点点变清楚的。最初我说的是端口被占了，接着发现自己还想找项目、打开项目、管理服务。真正开始开发，又不断遇到信息看不懂、操作接不上原有习惯的地方，再逐个调整。

我没有因为这些经历，就认定所有开发者都需要同样的工具。但对我来说，做它的理由已经足够具体。我会同时维护不同项目，也会继续让 Codex 参与开发，我需要一个地方把这些项目和正在运行的服务放在一起，看得明白，也能接着操作。

下次再看到端口被占用，我希望能直接找到它属于哪个项目，确认这个服务是否还需要，然后继续开发。
