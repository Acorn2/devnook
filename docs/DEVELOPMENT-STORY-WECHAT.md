# 端口又被占用了，于是我做了 DevNook

我做 DevNook 的起因，是开发时反复遇到的一句提示。

端口已被占用。

我同时开发多个项目，也会让 Codex 帮忙启动前端和后端。有时候服务已经跑起来了，我却不清楚本机还运行着哪些。等到自己再执行启动命令，看到端口冲突，才知道已经有一个进程占在那里。

原本只是想继续写点代码，却得先弄清楚，这是什么服务，属于哪个项目，还要不要留着。

这种麻烦反复出现以后，我就去网页版 GPT 里问，GitHub 上有没有开源工具，能帮我看清电脑到底启动了哪些服务。Node 也好，Java 也好，至少让我知道它们还在运行。

那时候，我还没有决定自己做一个产品，只想先找个现成工具，把问题解决掉。

继续聊下去，我又补充了自己的需求。光看见端口还不够，知道它被哪个进程占了，我还是得找到对应的项目。找到以后，可能要打开编辑器，可能要停掉旧服务，也可能只是想重启一下。这些事情散落在不同的地方，要我自己把它们连起来。

就连正常启动一个 Node 项目，也常常得先用开发工具打开目录，再切到终端，输入命令。我想要的方便很直接，选中项目以后，能少走几步，尽快进入开发。

我自己的工作里有 Java，也有 Node。Java 项目我习惯在 IDEA 里启动 application，其他服务又有各自的命令。只把终端里那一步搬进一个按钮，还不能涵盖我平时的用法，也得能用习惯的开发工具打开项目。

聊到这里，我才比较清楚，自己要找的是一个围绕本地项目的工作入口。端口冲突只是让我发现了问题，真正费事的，还有前后那些查找、切换和操作。

后来，我下载了 CodeDeck、localhost 和 Runbox，分别试着用了一下。

查看运行中端口的方式、扫描工程目录的过程，还有中文界面和菜单设计，这几款工具都有让我觉得顺手的部分。我当时在对话里表达得很直接，感觉需要把这三个项目合在一起，才是我真正想要的。

试用让我更清楚自己想要什么。我喜欢的几个环节分散在不同工具里，但实际开发时，我需要接着做下去。先找到项目，看它有哪些服务在运行，再决定要不要打开、启动或重启。尤其是 Codex 之前已经帮我启动的那些服务，也得能在这里找到。这些工具各有优势，我想把自己用得上的部分放到同一处。

于是，我开始做 DevNook。

这个过程没有变成直接合并它们的代码。参考项目帮我明确了想要的体验，DevNook 则围绕自己的使用流程逐步实现。

方向聊清楚了，做出来还是会有偏差。

有一轮，我启动了项目里的服务，却发现页面上看不到实际端口。我又追问，端口管理里既然能列出那些监听，为什么进入项目以后，却看不到它们和项目的对应关系？Codex、WorkBuddy 已经启动的服务，也应该能找回来。

即使已经有了启动和停止按钮，如果我还是看不清哪个服务用了哪个端口，最早的困扰就没有解决。

服务列表里还有一个很影响使用的地方，进程的技术名称比项目名更显眼，好几条记录看上去都是 node。可我想找的是自己的项目。都是 node，我还得看小字、认目录，才能分清谁是谁。

所以我又要求调整，全局先让我看到项目名，进入某个项目以后，再区分里面的服务。技术信息留着，需要排查时再看。

这些修改让我更清楚，打开这个窗口，我要的是认出自己的项目，知道它现在是什么情况，然后继续做事。发现的进程再多，认不出来，也还是麻烦。

比如我在项目目录里开着 Codex，它自己也可能有监听端口。这些信息放进项目服务页，很容易让人误以为项目的服务已经运行了。我还专门问过，这种东西有必要显示在这里吗，有人在乎吗？

我想看清的是 Codex 帮我启动的前后端，结果连 Codex 自己的监听也一起摆了进来。信息更多了，却更难判断。

后来，项目服务页收紧了范围。完整的端口信息仍然可以去查，日常页面则先展示我要管理的那些服务。这些调整没有让功能清单变得特别长，却让我觉得它离最初想要的东西更近了。

再往后，我又在开发对话里追问了一个问题。

原来由 Codex 启动的服务，如果改交给 DevNook 管理，以后是不是就只能由我自己点按钮启停了？

我还会继续用 Codex 写代码，让它检查日志、排查问题。如果把服务集中起来以后，反而要求我每次自己回来操作，原来的开发过程就被打断了。

最开始看参考项目时，我其实不太懂 MCP 有什么用，还专门问过。到了这里，我才有了能对应上它的具体需求，让 Codex 继续操作已经放进 DevNook 的服务。

至于通过命令还是其他接入方式，对我来说是后面的事。先要保证，我和 Codex 能找到同一份启动配置，看到同一个服务的状态。它需要重启的时候，能沿用这里已经保存的东西，不用再另外启动一份。

外部服务切换时，界面也得把事情说明白。保存了一份配置，旧服务可能还在跑；真正切换时，要让旧实例退出，再启动新的。页面如果只给一个含糊的状态，我还是会疑惑，到底哪个在运行，刚才的操作又做了什么。

后面的修改就在逐个处理这些困惑。配置和实际运行要分清，切换会做什么要讲明白，AI 后续怎么继续管理也要有入口。

回头看，DevNook 就是在这些反馈里一点点变清楚的。从端口冲突出发，我逐渐补齐了对找项目、打开项目和管理服务的要求；做出来以后，又通过实际使用，发现哪些信息看不懂，哪些操作接不上原有习惯，再逐个调整。

这些经历还不足以让我认定，所有开发者都需要同样的工具。但对我来说，做它的理由已经足够具体。我会同时维护不同项目，也会继续让 Codex 参与开发，我需要一个地方把这些项目和正在运行的服务放在一起，看得明白，也能接着操作。

下次再看到端口被占用，我希望能直接找到它属于哪个项目，确认这个服务是否还需要，然后继续开发。
